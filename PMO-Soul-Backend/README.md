# PMO-Soul-Backend

The new backend for Bright PMO: a NestJS + Prisma (PostgreSQL) API generated by
**Soul** (https://soul.adstek.co/) from `docs/target-schema.prisma`, then tuned
by hand. It replaces `PMO-Legacy-API` one feature at a time.

> **Status: generated and deployed (2026-10-18); runs locally on its own
> database; not yet used by the client.** This folder is Soul's generated
> backend, as exported. Before it holds real data, the generator issues in
> [SOUL-ISSUES.md](SOUL-ISSUES.md) must be fixed.

## What Soul generates, and what we use

Generating from our schema deploys **three applications**:

| Soul app | Who uses it | Our use |
|---|---|---|
| **Backend** (API) | the frontend | **Used.** NestJS 11 + Prisma 5.22: this folder. `PMO-Client` calls it through `/backend/...`. |
| **Frontend** | tenant users | **Not used.** `PMO-Client` is our frontend. Soul's generated screens can serve as a reference for its API calls. |
| **Admin panel** | the super admin, across all tenants | **Used for platform administration**: creating and managing tenants (organisations), their admins and the role matrix, much like Omnicure's super-admin view. `PMO-Client` therefore does not need its own tenant-management screens. In `PMO-Soul-Admin-Panel/`, runnable locally against this backend (see its README). |

## How the client reaches it

`PMO-Client` forwards `/backend/...` to `BACKEND_URL` (see
`PMO-Client/next.config.ts`). The browser only ever talks to the client's
origin, so no CORS setup is needed. Set `BACKEND_URL` to the API address
**including `/api`**, so `/backend/project` reaches `/api/project`.

| | Local | Deployed |
|---|---|---|
| Base URL (`BACKEND_URL` in `PMO-Client/.env`) | http://localhost:7062/api | _Soul's deployed API address_ + `/api` |
| Swagger / OpenAPI | http://localhost:7062/api/swagger | `/api/swagger` on the deployed API |

The port comes from `BACKEND_PORT`: 7062 in our local `.env`, 3001 inside
Soul's container.

## Running locally

Uses its own database, `pmo_soul`, on the same local PostgreSQL server as the
legacy API (never the legacy database, and never Soul's deployed one).

1. **Environment.** Copy `.env.example` to `.env` and fill in `DATABASE_URL`
   (database `pmo_soul`) and two random secrets. Soul's deployed settings, if
   you have them, belong in `.env.deployed` (git-ignored); they point at
   Soul's private network and do not work from a laptop.
2. **Database.** Create it once: `create database pmo_soul;`
3. **Install and set up:**

   ```
   npm install
   npx prisma generate          # npm 11 skips Prisma's own install script
   npx prisma db push           # creates the tables from prisma/schema.prisma
   npx ts-node prisma/seed.ts   # default organisation, two admin users, two roles
   ```

   The seed **deletes all users and roles first**: run it only on a fresh local
   database. It creates `admin@anothertestpmo.com` (super admin) and
   `orgadmin@anothertestpmo.com` (organisation admin); the password is printed
   by the seed.
4. **Start:** `npm run start:dev` (http://localhost:7062, Swagger at
   `/api/swagger`).

What does not work locally: workflows (they run on Soul's workflow engine),
in-app notifications (they need Redis on `localhost:6379`), email, file
uploads and reports. Plain records, sign-in, permissions and tenant scoping do.

Local changes to generated files (keep this list short, and re-apply after a
regeneration):
- `tsconfig.build.json` leaves out `src/shared/preview-worker.ts`, Soul's
  in-browser preview code, which does not compile (SOUL-ISSUES.md, issue 11).
- `.gitignore` has its indentation removed, so it works (issue 13), and keeps
  `.env.example`.

## Soul trial import: findings

| Question | Finding |
|---|---|
| **Schema features** | **Composite ids rejected**, so `WorkItemAssignee` and `CommentMention` have a surrogate `id` plus `@@unique` on the pair. Everything else parses. **But the generated code drops several features without warning**; see "How well it reflects our schema". **Built-in models** replace ours of the same name; see "Soul's built-in models". |
| **Tenant isolation** | **Yes, and well.** Soul adds `organizationId` to 88 of its 99 tables (child tables like `WorkItem` included). A Prisma middleware filters every read by the caller's organisation, stamps it on every write, and checks ownership on single updates and deletes. Our own `organizationId` columns are kept and are the same column. |
| **Sign-in** | Soul issues its own JWT (1 day) from `POST /api/auth/login` (email + password) or a one-time email code; `POST /api/auth/refresh` renews it. The token is read **only from `Authorization: Bearer`**, never a cookie. It carries the user id, email, role name, permissions and organisation. **No SSO / IdP sign-in.** Passwords are bcrypt, so hashes migrated from the legacy `bcryptjs` keep working. |
| **REST conventions** | Prefix `/api`; singular lowercase routes (`/api/project`, `/api/workitem`). List: `GET /api/project?page=0&limit=10&sortBy=&sortOrder=&q=` returns `{ data, total }`, **0-based page**, default 10, max 100. Filters: `?field=value` for equality, or `?field_op=value` with `contains`, `startsWith`, `endsWith`, `gt`, `gte`, `lt`, `lte`, `ne` (e.g. `status=active`, `budgetAmount_gte=1000`); one operator per field (issue 14). The `q` search fails on tables with list columns (issue 15). `POST /api/<entity>/aggregate` gives sum/avg/min/max/count for dashboard cards. Related records: `GET /api/project/:id/<relation>` returns the parent **with** the relation included. Decimals arrive as strings. Unknown body fields are refused with 400. Errors use Nest's `{ statusCode, message, error }`. |
| **Swagger / OpenAPI** | Yes, at `/api/swagger`. |
| **Custom code** | Two routes: Soul's **workflow engine** (below) for side effects, and hand-written NestJS modules for read views and calculations. _To confirm with Soul:_ where hand-written code lives so that regenerating does not overwrite it. |
| **Code export / Git** | Yes: the generated backend is this folder. Its `.env` files are git-ignored. |
| **Database access** | _Open._ The database address in the generated `.env` is on Soul's internal network. The data migration needs an externally reachable connection, or an import route, from Soul. |

## How well it reflects our schema

**Kept:** all 78 tables (each a module with create, list, get, update, delete,
relation routes and an aggregate route), all 68 enums, all relationships,
`Decimal`, arrays, `Json` and self-relations. Soul adds 21 platform tables of
its own (`Agent*`, `Auth*`, `Workflow*`, `Mail`, `Dashboard*`, …).

**Dropped by the generator:**

| Lost | Effect |
|---|---|
| All 30 composite `@@unique` rules | Duplicate work-item keys per project, duplicate project codes per organisation, duplicate dependencies between two tasks, two timesheets for one user and week all become possible. |
| Field defaults (only ids and `createdAt` kept) | Create requests must send `status`, `workItemSeq`, `progressPct`, `healthScore`, cost fields and so on. `createdById` is **required from the client**, so it can be spoofed. |
| 55 of our cascade deletes | Deleting a project, sprint or comment with children fails. |
| Required relations (all became optional) | A project without a manager or organisation, a work item without a project, is accepted. |
| `@map`/`@@map` and `@db.Decimal` precision | Tables and columns are camelCase. Matters only for the data migration. |

## Waterfall and Agile

The data model supports both, but **nothing behaves differently**: methodology
is just a field and creating a project inserts one row. There are no default
work-item statuses, no work-item numbering, no root WBS node, no sprint rules,
no critical path, no roll-ups and no approval. All of "Logic that will need
custom code" is still to build.

## The workflow engine

Workflows start on a record being created, updated or deleted, on a schedule,
from a public webhook (with a secret) or from a button. Steps can create,
update or query records, move a status only along allowed transitions, check a
condition, branch and loop, wait for a person (a task inbox with "complete
task" endpoints), notify, email and call the app's own API.

**Use it for:** PJM -> ADMIN approvals (project creation, closure, budget
changes), status transition rules, notifications and reminders, scheduled jobs
(recurring work items, weekly timesheets), closure checks, and new-project
setup (default statuses and starting records).

**It cannot:**
- **Return data.** Starting a workflow returns only `{ status, runId }`, so
  boards, backlogs, Gantt, burndown and dashboards need read endpoints.
- **Calculate heavily.** A code step is sandboxed: 1 second, synchronous, no
  database access. Critical path over a project will not fit.
- **Block a bad save.** Record triggers run after the write and never fail it.
  Rules like WIP limits or "dependency not finished" need a screen-started
  workflow instead of a direct edit, or code.
- **Serve screens through webhooks.** They are public and run with no signed-in
  user, so they suit system integrations (finance, HR) only.

**Watch out:** a field owned by an active workflow (e.g. `Project.status`) is
refused in any create or update request (`workflow-controlled-fields.ts`). With
defaults dropped, the create request *requires* `status`, so an approval
workflow on `Project.status` would make projects impossible to create until
Soul honours `@default`.

## Soul's built-in models

Soul always adds seven models and skips any model of ours with the same name.
`docs/target-schema.prisma` mirrors the built-ins exactly (as exported on
2026-10-18), so the file stays valid and true to what Soul generates.

| Soul built-in | What it replaced in our schema | What we did with our fields |
|---|---|---|
| `Organization` (name, slug, colours, isActive) | `Organization` | `status`, `idpOrganizationId`, `timezone`, `defaultCurrency`, `logoStorageKey`, `settings` moved to a new `OrganizationSettings` table (one row per organisation). |
| `BusinessUnit` (organisation -> units) | nothing | Replaces our free-text `User.department`. Users also carry their own `organizationId` (added by Soul), which is what tenant scoping uses. |
| `User` (first/last name, email, password, roleId, businessUnitId) | `User` | `username`, `idpUserId`, `phoneNumber`, `status`, `lastLoginAt` moved to a new `UserProfile` table (one row per user). `password` is required: IdP-only users get an unusable placeholder. Our `organizationId` on users is gone; the cross-tenant administrator is Soul's super admin (answer 4 below). |
| `RolesAndPermissions` (role name + entityPermissions JSON) | `Role` + `RolePermission` | Both dropped. Approval steps (`ApprovalPolicyStep.approverRoleId`) now point at `RolesAndPermissions`. The 13 legacy roles (ADMIN, PJM, PMO, FIN, PROC, ENG, SITE, QAQC, IT, DIR, HR, LEGAL, SYSTEM) are its rows, created by `migration/`. A role name is unique across the whole application, so two tenants cannot both have a role called ADMIN. |
| `Notification` (title, message, channel, level, isRead, entityName/RecordId, processType, metadata) | `Notification` | Our type -> `processType`, priority -> `level`, linked record -> `entityName` + `entityRecordId`. Our three notification enums were removed. |
| `SavedReport` (name, definition JSON, allowedRoleIds, isActive) | `ReportDefinition` (dropped) | Our `format` goes inside `definition`. |
| `Workflow` (entity, definition JSON, version, status) | partly `WorkflowRule` | **Kept `WorkflowRule` for now.** Drop it once Soul's workflow engine is shown to express its triggers and actions (it very likely can; see "The workflow engine"). |

**Reserved names.** Soul skips our models that share a built-in's name, but
not names that clash with its built-ins' internal enums. Our model
`WorkflowStatus` broke the first deployment ("Cannot set a default value on a
relation field", P1012, on the built-in `Workflow.status`), so it was renamed
`WorkItemStatus` (table `work_item_statuses`). Avoid naming a model or enum
after a built-in model plus a suffix (`WorkflowStatus`, `UserRole`,
`NotificationType`, …); a P1012 error on a built-in model points to another
clash of this kind.

Answers from Soul (2026-10-18):
1. **Built-in models cannot be changed** (no fields added or removed). So the
   extension tables are permanent: `UserProfile` and `OrganizationSettings`
   hold our extra fields, one row each, linked to the built-in by a unique key.
   Every relation keeps pointing at the built-in `User.id` / `Organization.id`
   (the identity Soul authenticates and scopes by); only these two tables point
   at the profile data. A profile/settings row is created whenever a user or
   organisation is (a record-created workflow can do this).
2. **`entityPermissions` is per entity and per action** (get, list, create,
   update, delete, plus named actions), like Omnicure's matrix. The generated
   guard confirms it is **yes/no only**: there is no `own` scope. Row-level
   rules ("a PJM edits only their own projects") are therefore custom backend
   code; see "Logic that will need custom code".
3. **Text ids on `Notification` and `SavedReport` work in Soul**, so we use them
   as they are: treat ids there as opaque strings and write `String(user.id)`
   when creating a notification or report.
4. **Soul has a super admin** for the whole application across all tenants. A
   tenant admin administers exactly one tenant. This replaces our design's
   "user with no organisation". Note that `User.email` is unique across the
   whole application, so one person cannot have accounts in two tenants with
   the same email.

## Logic that will need custom code

Roughly 80% of the backend is generated CRUD plus workflows. The rest needs
hand-written NestJS modules:

- Critical-path calculation and progress roll-ups
- Board and backlog queries; sprint start and complete
- Burndown, velocity and earned value
- Row-level access, since permissions are yes/no per action: a PJM edits only
  projects they manage, users see and edit only their own timesheets, members
  see work items only in projects they belong to
- Status-change checks that must block the save (WIP limits, unfinished
  dependencies, open subtasks)
- Work-item numbering (`PRJ-1`, `PRJ-2`, …) without gaps or duplicates
- Timesheet approval and its cost effects

Workflows cover: the approval engine (PJM -> ADMIN), transition rules,
notifications, closure checks, scheduled jobs (recurring tasks, weekly
timesheets) and new-project setup.

## Integrating with PMO-Client

1. **Fix the generator issues first** ([SOUL-ISSUES.md](SOUL-ISSUES.md)), at
   least the security ones, before any real user or data is added.
2. **Point the client at it:** `BACKEND_URL` in `PMO-Client/.env`, ending in
   `/api`.
3. **Bridge sign-in.** The sign-in screen logs in to Soul (`/api/auth/login`),
   keeps the token for `/backend` calls (sent as `Authorization: Bearer`) and
   refreshes it before it expires. While features still use the legacy API, it
   logs in to both with the same email and password. IdP sign-in is not
   available through Soul without custom work.
4. **A backend HTTP client plus one `api.ts` per feature** that translates
   Soul's conventions into the client's: 0-based pages, `field_op` filters,
   decimal strings to numbers, ids to names (managers, categories) through
   lookups, Nest error messages to toasts.
5. **Permissions in the UI** from the token's per-entity permissions
   (`backendCan` in `PMO-Client/src/lib/backend`). The 13 roles and their
   matrix come from `migration/role-matrix.mjs`.
6. **Pilot one simple feature end to end** (Portfolios or EPS), then move
   feature by feature: projects, work items, Waterfall, Agile.
7. **Migrate the legacy database** into organisation #1 "Wujha" (UTC, EGP)
   with the scripts in `migration/` (see its README). Organisation, business
   units, roles and users are done and run against the local database; the
   deployed database needs access from Soul.
