# Create User Account (`identity.createUser`)

Creates a login for someone and emails them an invitation to choose their own password. The only
step in the catalogue that may create one.

Use it for a process that creates an account for **somebody else**: an approved application, an HR
import, a new client. Public self sign-up is not a workflow: it is a switch in
**Settings → Sign-in & Email**, and the sign-up route creates the account itself.

## Why this and not `data.createRecord`

`data.createRecord` *can* address the `User` model — nothing excludes it, and the tenant middleware
would stamp the organisation — but it cannot do the things that make creating a login safe:

1. **It takes its whole payload from author-typed JSON**, which may template a value from the data.
   One `{{record.roleId}}` in the wrong field and the data chooses its own role.
2. **It cannot refuse an administrator role**, because it does not know what a role is.
3. **It cannot get the person in.** It would have to write a password, and a password in a workflow
   sits in run history.

So this pulse exists, with a narrow contract instead of a free-form payload.

## Config

- **Email** (required) — who the account is for, usually a template such as `{{record.email}}`.
  The invitation goes to this address.
- **First name / Last name** — optional, usually templates.
- **Role to grant** (required) — the NAME of the role, e.g. `Member`. Looked up on the role model.
  A role that can write the roles table, or that carries an `isPlatformAdmin` / `isAdmin` /
  `isSuperAdmin` flag, is **refused** (`AdministratorRoleRefused`): a workflow may not mint an
  administrator. The test is what the role can DO, not what it is called.
- **Organisation** — the organisation id for the new account. Blank means the run's own
  organisation (the workflow's tenant).
- **User entity / Role entity / Role name field** — defaults `User`, `RolesAndPermissions`, `role`.
  Present because a schema may name these differently; an app generated by Soul does not need them
  changed.

## What it writes

A fixed whitelist: `email`, `firstName`, `lastName`, `roleId`, `organizationId`. **No password**:
the account is created without one and the person chooses it through a single-use emailed link,
so nothing the workflow holds is ever a credential. `isPlatformAdmin`, `entityPermissions` and any
other privilege column cannot be reached from this step however a variable is set.

- **Outputs:** `user` — the created row with every credential key stripped; `invited` — whether the
  emailed link went out (if not, an administrator can re-send it from the Users page).
- **Errors:** `MissingRole`, `MissingEmail`, `InvalidEmail`, `InviteNotAvailable`, `RoleNotFound`,
  `AdministratorRoleRefused`, `EmailTaken`. All catchable business errors, so a graph can branch on
  them.
