# PMO-Backend

The new backend for Bright PMO: a NestJS + Prisma (PostgreSQL) API generated by
**Soul** (https://soul.adstek.co/) from `docs/target-schema.prisma`, then tuned
by hand. It replaces `PMO-Legacy-API` one feature at a time.

## How the client reaches it

`PMO-Client` forwards `/backend/...` to `BACKEND_URL` (see
`PMO-Client/next.config.ts`). The browser only ever talks to the client's
origin, so the sign-in cookie and the `Authorization` header reach this backend
the same way they reach the legacy API.

## Soul trial import: findings

Import `docs/target-schema.prisma` and record what Soul does with each point.

| Question | Finding |
|---|---|
| **Schema features**: does it accept `@map`/`@@map`, `Decimal` with precision, array columns (`Int[]`, `String[]`), composite ids (`@@id`, e.g. `WorkItemAssignee`), self-relations (WorkItem parent, EPS and WBS trees), `Json`? List anything rejected. | |
| **Tenant isolation**: does it scope rows by `organizationId` itself? If not, a tenant guard and query filter must be added before it holds real data. | |
| **Sign-in**: can it verify our PMO/IdP JWT (HS256 with `JWT_SECRET`, or the IdP's keys)? If so, one sign-in covers both backends. How do its own users and roles relate to our `User`/`Role` tables? | |
| **REST conventions**: URL shape, pagination format, filtering and sorting, error format. | |

| **Code export / Git**: can the generated code be exported or pushed to a repository? | |

## Logic that will need custom code

Generated CRUD should cover most of the ~75 models. The following needs custom
endpoints or tuning, per the backend plan:

- Status transitions and their checks (WIP limits, dependencies, open subtasks)
- Sprint start and complete; board and backlog queries
- Critical-path calculation and progress roll-ups
- The approval engine (PJM -> ADMIN for project creation and closure)
- Burndown and velocity
- Timesheet approval and its cost effects
- Closure auto-checks
- Scheduled jobs (recurring tasks, weekly timesheets)
